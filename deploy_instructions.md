# XPLORA Cloud Deployment Guide 🚀

This guide explains how to deploy the React frontend to **Vercel** and the FastAPI backend service to **Render** directly from your GitHub repository: `https://github.com/ryan1234814/XPLORA-Travel-Agent`.

---

## 📡 1. Deploy the Backend to Render

Render will read the `render.yaml` specification in the root of the repository to spin up a persistent Python Web Service. The blueprint provisions **only the backend** — the frontend is deployed to Vercel (Step 2).

### Steps:
1. Sign in to your [Render Dashboard](https://dashboard.render.com).
2. Click **New +** in the top right, then select **Blueprint**.
3. Connect your GitHub repository (`XPLORA-Travel-Agent`).
4. Render will auto-detect the service described in `render.yaml` (named `xplora-backend`, Python 3.12, health check at `/`).
5. Render will prompt you to input the values for the following environment variables:
   - **Required:**
     - `GROQ_API_KEY`: Your Groq platform key.
     - `DATABASE_URL`: the **pooled** Neon connection string (see Database Setup below).
     - `JWT_SECRET`: generated by Render (`generateValue: true` in `render.yaml`).
     - `CORS_ORIGINS`: your Vercel URL, e.g. `https://xplora-travel-agent.vercel.app`.
       Session cookies need credentialed CORS, so `*` is not usable here.
   - **Recommended / optional** (leave blank to disable the feature):
     - `OPENROUTER_API_KEY`: Fallback LLM when Groq is at capacity.
     - `TOMORROW_IO_API_KEY`: Your weather API key (falls back to free Open-Meteo).
     - `SCRAPEGRAPH_API_KEY`: Scraper key reserved for future use.
     - `GOOGLE_PLACES_API_KEY`: Place photos/ratings enrichment.
     - `EXCHANGERATE_API_KEY`: Currency conversion.
     - `PINECONE_API_KEY`: RAG knowledge base for travel blogs.
6. Click **Apply**. Render will automatically provision the service, install requirements, boot uvicorn, and verify the `/` health endpoint.
7. **Copy the Web Service URL** (e.g. `https://xplora-backend.onrender.com`). You will need this for the Vercel frontend.

### 🗄️ Database Setup:
Neon hosts a free serverless Postgres, and the app creates its own tables on startup:
1. Create a project at <https://console.neon.tech> (or `neon projects create --name xplora-travel --database travel_agent`).
2. Copy the **pooled** connection string — it ends in `-pooler...neon.tech` — into `DATABASE_URL`.
   Always use the pooled endpoint for a serverless backend; the direct endpoint exhausts connections.
3. Keep `sslmode=require` in the string; Neon rejects plain connections.
4. Set `AUTH_COOKIE_SECURE=true` (the default in `render.yaml`) since the app is served over HTTPS.

## ⚡ 2. Deploy the Frontend to Vercel

Vercel will build and host your Vite/React static assets.

### Steps:
1. Sign in to your [Vercel Dashboard](https://vercel.com/dashboard).
2. Click **Add New** -> **Project**.
3. Import your GitHub repository (`XPLORA-Travel-Agent`).
4. In **Project Settings**:
   - Vercel automatically detects **Vite** as the framework.
   - **Root Directory**: Select `.` (Default).
   - **Build Command**: `npm run build` (Default).
   - **Output Directory**: `dist` (Default).
5. Open **Environment Variables** and add the following variable (⚠️ **required — the app will not work without it**):
   - **Key**: `VITE_API_BASE_URL`
   - **Value**: `https://your-backend-url.onrender.com` (paste your Render backend URL copied in Step 1).
   - Note: Vite bakes this value in **at build time**. If your backend URL changes, update the variable and **redeploy** Vercel.
6. Click **Deploy**. Vercel will install dependencies, build the client, and serve the application!

## ✅ 3. Post-Deploy Verification Checklist

1. **Backend health**: Open `https://your-backend-url.onrender.com/` — it should return JSON like `{"status": "ok", "service": "xplora-backend", ...}` with HTTP 200. Render keeps the service "Live" only if this check passes.
2. **Frontend wiring**: Open the live Vercel URL, start a trip request, and check the browser Network tab — every `/api/*` request must go to `*.onrender.com`, **not** the Vercel domain. If a console error says `VITE_API_BASE_URL is not set`, add the env var in Vercel and redeploy.
3. **CORS / cookies**: Requests succeed from the Vercel origin. `CORS_ORIGINS` on Render must list the exact Vercel URL — the session cookie is sent with `Access-Control-Allow-Credentials`, which a wildcard origin cannot satisfy. A `/api/auth/me` call returning 200 with `Set-Cookie` proves it.
4. **Database**: Sign up, generate a trip, then open `/dashboard` — the trip must be listed and reopenable. That confirms Neon accepts connections from Render (Neon allows any IP by default; enable IP Allow only if you add Render's egress ranges).

## 🔄 4. Continuous Integration
Whenever you push new changes to the `main` branch of your GitHub repository:
- **Vercel** will automatically rebuild and redeploy the frontend client.
- **Render** will automatically pull, install dependencies, and rebuild the FastAPI backend.

## 💤 5. Keeping the backend awake

Render's free tier stops the service after ~15 minutes with no traffic. The next
visitor then waits out a 30–60s cold start, which looks like a broken site.

**The live backend is `https://xplora-backend-b3gn.onrender.com`.** The older
`xplora-backend.onrender.com` service is suspended and answers `503 Service
Suspended` — the Vercel project's `VITE_API_BASE_URL` must point at the live
one, and Vite bakes that value in at build time, so changing it requires a
redeploy.

Two layers keep the service warm:

1. **`.github/workflows/keep-alive.yml`** pings the health endpoint on a 10-minute
   cron. It retries through cold starts, verifies the second (warm) response, and
   runs once after every push to `main`. It can be run on demand from
   *Actions → Keep backend awake → Run workflow*.

2. **An external pinger — required for real uptime.** GitHub heavily throttles
   `schedule` triggers on low-activity repositories; in practice this cron fires
   hours apart, so the workflow alone cannot keep a 15-minute idle timer from
   expiring. Register the health URL with a free monitor that checks every
   1–5 minutes:

   - [cron-job.org](https://cron-job.org) — free, 1-minute interval: create a job
     for `https://xplora-backend-b3gn.onrender.com/` with method `GET`, and enable
     "Save responses in job history" off.
   - [UptimeRobot](https://uptimerobot.com) — free plan, 5-minute HTTP(s)
     monitor (still under the 15-minute sleep window, and it emails you if the
     backend really goes down).

   Either one is enough; UptimeRobot also covers alerting, so it is the better
   single choice. Keep the GitHub workflow as a second layer.

**Verify the setup** at any time:

```bash
curl -s -o /dev/null -w 'HTTP %{http_code} in %{time_total}s\n' --max-time 120 \
  https://xplora-backend-b3gn.onrender.com/
```

A warm backend answers `200` in about a second. Anything over ~20s means the
service had gone to sleep, and multiple `503`s over several minutes mean it was
suspended by Render — open the Render dashboard and check the service status.
